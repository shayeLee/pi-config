# Iterative Work

你要以可验证、可停止、逐轮收敛的方式完成以下任务。

- **用户输入**：`$ARGUMENTS`

输入语法：

```text
`<目标>` [约束或上下文]
```

- 若用户输入以一对反引号开头：首个完整反引号对中的内容是**目标**；该闭反引号后的全部文本（忽略开头空白）是**约束或上下文**。
- 若用户输入不以反引号开头：仅当整段输入可无歧义地作为一个目标时，将整段视为**目标**，约束为空。
- 若未提供目标，或输入看似同时包含目标和约束但没有用首个反引号对分隔，停止并要求用户按上述语法重新输入；不要猜测或自行拆分。

## Loop State

每轮开头必须输出一个可见的状态块；在 `decide` 后根据结果更新它，不能遗漏任何一轮的开头状态：

```text
Loop State
- iteration: n / budget
- work done: <已完成的工作>
- verified items: <已验证的事项>
- open risks: <未解决的风险>
- current testable hypothesis: <当前可测试假设>
- this iteration's action/delegation plan: <本轮行动/委派方案>
- status: <initializing / in progress / blocked / completed / stopped>
- current objective: <本轮要推进的目标>
- last observation: <最近观察到的事实>
- verification: <本轮验证方法>
- progress: <无 / 有限 / 实质进展，以及依据>
- stop state: not stopped
```

其中仅首轮可为 `initializing`，后续轮次采用上轮 Decide 更新后的实际状态。

## Loop Specification

在采取任何行动前，先声明以下规范；不确定之处明确标为假设，不得伪装成事实：

- **目标**：要达成的具体结果，以及用户输入的可操作解释。
- **成功标准**：可观察、可验证、尽量可重复的完成条件。
- **范围**：本次允许触及的文件、系统、操作和外部对象。
- **非目标**：明确不做的工作，包括无关重构和未授权操作。
- **约束**：从用户输入中提取的约束或上下文；若为空按无处理；以及权限、安全、时间、成本和兼容性要求。
- **已知事实/假设**：分别列出已确认事实与待验证假设。
- **验证**：每个成功标准对应的命令、检查或其他可复现验证方法；记录预期结果。
- **baseline**：行动前的当前状态、基线命令输出或已知失败/缺口。
- **可测试假设**：本轮准备验证的一个具体假设，以及支持或否定它的证据。
- **行动/委派方案**：在范围和预算内，选择能检验该假设并推进目标的执行与委派方案。
- **执行上下文**：当前可用的能力，以及环境是否提供可用的委派能力。
- **默认保守具体预算**：若用户未另行指定，最多 6 轮。
- **预算语义**：一轮从 Observe 开始，到该轮所有既定直接行动/委派返回并完成 Verify、Decide 为止；执行与委派方案的内部步骤不额外计轮。每轮结束后若已达适用轮次预算（用户指定，否则为 6 轮），不得开启新的 Act/Delegate；报告 `iteration budget exceeded`，但已在本轮完成的验证仍要记录。
- **状态**：`initializing`、`in progress`、`blocked`、`completed` 或 `stopped` 之一，并说明依据。
- **停止状态**：当前是否满足停止条件；若停止，写明触发的条件和最后证据。

## 逐轮协议

每一轮必须严格遵循：`observe -> act/delegate -> verify -> decide`。不得跳过、合并或在验证前宣布完成：

### 1. Observe

读取当前状态和相关材料，核对上轮结果、范围、预算与停止条件。只记录事实和明确标注的假设。若无法获得必要信息，先将其作为阻塞状态，不猜测替代。

### 2. Act / Delegate

由模型根据依赖、风险、冲突和验证需要，自行设计合适的执行与委派方案；不得扩大范围、顺手清理或引入未授权的步骤。若 Observe 已确认成功标准全部满足或已确认阻塞，Act / Delegate 记录 `no action` 和依据；行动前说明执行方案、预期变化及回滚方式（如适用）。

### 3. Verify

立即按 Loop Specification 中的验证方法检查结果，不得把“命令已运行”当作成功。每项验证都记录：

```text
Verification
- command/check: <实际命令或检查>
- exit code: <退出码；非命令检查说明结果>
- summary: <简短、基于证据的摘要>
- result: pass / fail / inconclusive
```

若验证失败或结果不确定，保留原始证据，更新状态和假设，不要无依据重试或扩大行动。

### 4. Decide

根据观察和验证结果，只做一个决定：

- **完成**：所有成功标准均已验证，进入最终汇总。
- **继续**：如实指出本轮进展等级（无、有限或实质）及依据，随后更新可测试假设并确定下一轮行动/委派方案。
- **阻塞**：缺少权限、信息或外部条件；停止并报告需要谁提供什么。
- **停止**：触发停止条件，停止行动并报告证据。

同一个行动/委派方案连续失败两次时，升级 `rescue`。
连续三轮没有实质进展时停止。

## 最终汇总

完成或停止时输出最终汇总，保持简洁但完整：

1. 目标与最终状态。
2. 成功标准逐项结果及证据。
3. 完成的行动/委派方案和实际变更（如有）。
4. 每轮验证命令或检查、退出码和摘要；失败或不确定项也必须列出。
5. 采用或否定的关键假设、剩余风险和未完成事项。
6. 若停止，明确停止条件、原因，以及继续所需的下一项输入、决策或授权。
