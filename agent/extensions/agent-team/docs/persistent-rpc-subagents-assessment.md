## 1. 背景与当前一次性子进程架构

`agent-team` 扩展向 Pi 注册 `subagent` 工具，通过**独立 Pi 子进程**运行项目级 / 用户级子角色（`worker` / `reviewer` / `lite` 等）。其核心数据流（见 `agent/extensions/agent-team/README.md` 与 `index.ts`）为：

1. 主代理调用 `subagent`；
2. `agents.ts` 按 `agentScope` 发现角色 Markdown，读取其 frontmatter 与正文；
3. 角色正文写入权限 `0600` 的临时文件，通过 `--append-system-prompt <临时文件>` 传入子进程，调用结束后删除；
4. 任务以 `Task: <task>` 形式作为单条进程参数传入（使用 `shell: false`，不经过 Shell 展开）；
5. 扩展以等价参数启动子进程：

   ```text
   pi --mode json -p --no-session
   ```

   并追加 `--model <model>`、`--tools <逗号分隔工具名>`、`--append-system-prompt <临时文件>`；
6. 解析子进程按行输出的 JSON 事件（`message_end`、`tool_execution_update/end` 等），提取最后一条含 `text` 的 assistant 消息作为最终文本；
7. `content`（进入主代理上下文）与 `details`（结构化完整记录，供 TUI / 日志使用）返回；临时文件与临时目录删除。

### 当前架构的关键事实（决定方案 2 的改造面）

- **每个调用都是一次性子进程**：Single / Parallel / Chain 的每一步都 `spawn` 一个全新的 `pi --mode json -p --no-session` 进程，结束即退出。
- **独立上下文窗口、上下文隔离**：每个子代理拥有独立 Pi 进程与独立上下文；父代理的会话历史、附件、工具结果、隐含上下文**不会自动复制**给子代理，因此 `task` 必须自包含（目标、范围、约束、相关路径、已有发现、验收方式）。
- **`--no-session` 表示子代理不保存可恢复会话**：“隔离”是上下文与进程隔离，不是文件系统 / 命令权限沙箱。
- **Chain 的 `{previous}` 仅传递上一步“最终 assistant 文本”**，不含完整消息、工具结果或 `details`，且不泄漏中间过程。
- **Parallel 边界**：一次最多 8 个任务，最多 4 个并发子进程，结果保持输入顺序，单任务文本上限 50 KiB，单任务失败不阻断其他任务。
- **停止语义**：POSIX 向独立进程组发 `SIGTERM`，5 秒后仍有成员则 `SIGKILL`；Windows 用 `taskkill /T`。停止针对单个子进程。
- **两层分离契约**：数据流层（`agents.ts` + `index.ts`）与展示层（`fleet-view.ts` + `fleet-web.ts`）通过中立契约 `FleetStore` 单向解耦，展示层只读消费。
- **当前不支持运行中 steer**：子进程使用一次性 `--no-session` print 模式。

### 方案 2 的动机

上述一次性架构在**同一角色被高频、连续调用**的场景下存在重复成本：每次都要重新 `spawn`、重新加载角色系统提示词、重新发现项目上下文，且子代理无法在多次调用间“记住”已完成的工作。方案 2 提议改为**常驻的 `pi --mode rpc` 进程**：为每个（角色 × 会话分支）维持一个长生命周期 RPC 会话，在多次 `subagent` 调用之间**复用同一上下文窗口**，从而避免重复冷启动、并让子代理跨调用保留对话历史。

## 2. 结论与工时

**结论：技术上可行，但收益与复杂度的平衡点尚未明确，且精确的生命周期 / 分支 / 并发语义存在显著不确定性与回归风险。建议保持 deferred，先做最小可行性验证。**

工时测算（人日，按单人等价估算，已含测试与文档，不含真实 TUI / 浏览器手测协调时间）：

| 阶段 | 范围 | 工时 |
| --- | --- | --- |
| 验证（feasibility spike） | 仅验证“常驻 `pi --mode rpc` 能稳定复用上下文并正确返回结果”这一假设，不改主路径 | **1–2 人日** |
| 受限 MVP | 单会话、单分支、单角色串行复用的受限实现（见第 4 节边界） | **5–8 人日** |
| 生产就绪 | 在上述基础上补全生命周期、容错、可观测与回归保护，但**不含**精确跨重启 / 分支 / 同角色并行 | **15–25 人日** |
| 全量（含精确跨重启 / 分支 / 同角色并行） | 在生产就绪基础上，额外实现跨主进程重启恢复、session 分支隔离、同角色并发复用 | **20–35 人日** |

> 说明：“生产就绪 15–25 人日”与“全量 20–35 人日”区间存在重叠，反映跨重启 / 分支 / 同角色并行这三者既可部分叠加、也可按需裁剪；若只做其中一项或两项，工时落在两区间的低段；三者全做则接近 35 人日。

## 3. 核心改造点与风险

### 3.1 核心改造点

1. **进程模型从“每次 spawn”改为“按需常驻 + RPC”**
   - 引入子代理进程池 / 注册表，按 `角色 × 会话分支` 维度复用 `pi --mode rpc` 长生命周期进程，替代 `index.ts` 中每次调用 `spawn("pi", ["--mode","json","-p","--no-session", ...])` 的写法。
   - 调用时若对应 RPC 会话已存在则复用，否则惰性启动。

2. **上下文复用与任务注入方式变更**
   - 角色系统提示词只在第一帧注入；后续 `subagent` 调用通过 RPC 提交 `task`，上下文窗口自然累积历史，不再每次重建 `--append-system-prompt` 临时文件。
   - 需要明确：多轮历史在上下文中如何截断 / 压缩，避免无限增长。

3. **生命周期与停止语义重构**
   - 当前“停止 = 向进程组发 `SIGTERM`/`SIGKILL`”的对象从一次性子进程变为常驻 RPC 会话；需新增“优雅关闭单个 RPC 会话、关闭整个分支的所有会话、主进程退出时兜底回收”的协议。
   - 需要重新实现 `FleetStore` 控制端口对常驻会话的停止 / 取消。

4. **`{previous}` 与 Chain 语义的重新定义**
   - 在复用上下文后，`{previous}` 是否仍按字面注入、或改为“上下文已包含上一步、无需注入”需重新决定（见第 5 节）。

5. **Fleet / TUI / 只读 Web UI 的可观测性适配**
   - 展示层从“消费一次性调用的 `SingleResult`”变为“订阅常驻会话的增量事件流”；需保持现有数据 / 展示分离契约不被破坏（两块自动 harness 守护）。

### 3.2 主要风险

- **回归风险高**：现有 `harness/run.mjs` 用 fake `pi` 断言“每次 spawn 一次性进程、停止走进程组信号、chain 不泄漏中间过程”。改为常驻 RPC 后，这些断言的等价性与进程组终止覆盖后代的语义需要重新设计与守护。
- **上下文污染**：复用上下文若不做边界隔离，一个 `task` 的副作用（错误假设、误读结果）会污染后续 `task`；当前“`task` 自包含 + 独立窗口”天然隔离了这一点。
- **资源与泄漏**：常驻进程若未被正确回收，会造成进程 / 文件句柄 / 上下文 token 泄漏；主进程异常退出时的孤儿 RPC 进程需兜底。
- **跨重启 / 分支语义复杂**：主进程重启后，`pi --mode rpc` 会话无法自动存活，需要持久化（恢复点 / 重放 / 重新冷启动）策略；session 树分支意味着同一角色在不同分支应有不同上下文视图。
- **同角色并行冲突**：多个并发任务复用同一角色上下文时，串行追加会相互交错，需要决定“串行排队”还是“每并发任务独立 RPC 实例”。
- **可观测性断层**：常驻会话的流式进度、停止确认（连续两次 `x`）、浮层 15 秒保留 / 32 条上限等现有行为需重新映射，否则 TUI / Web UI 出现状态错乱。

## 4. 推荐的受限 MVP 边界

为避免一上来就触碰全部不确定点，建议（若未来决定开工）MVP **严格限制**在以下边界内，不超出即回到一次性架构的等价行为：

- **仅单会话、单分支**：不考虑跨重启恢复、不考虑 session 树多分支隔离。
- **仅单角色串行复用**：同一（角色 × 分支）在同一时刻只维护一个 RPC 会话，并发的同角色 `subagent` 调用串行排队，不引入“每并发任务独立实例”。
- **仅 Single 模式试点**：先支持单个 `subagent` 调用复用上下文；Parallel / Chain 暂不改写，继续走一次性子进程路径（保持与现状一致）。
- **`task` 仍要求自包含**：即使上下文已累积，MVP 阶段不改变调用方契约，避免隐藏依赖。
- **显式 `ttl` / 空闲回收**：RPC 会话在空闲超过阈值后自动优雅关闭并回到一次性路径，防止泄漏。
- **保留现有停止语义的等价实现**：MVP 必须仍能被 `SIGTERM`/`SIGKILL` 与 Fleet 停止端口正确终止，且 `exitCode 130` / `stopped` 状态、`interrupted` 历史态不变。

超出以上任一边界即视为超出 MVP、进入“生产就绪”乃至“全量”阶段。

## 5. 实施前待定的产品语义（必须澄清后才能开工）

以下开放问题在 **deferred 期间不解决**，但一旦决定实施，必须先给出明确答案，否则会回退为重新设计：

1. **复用粒度的产品定义**：复用上下文是“同一角色跨调用记住历史”，还是“同一业务任务的多轮协作”？前者简单、后者语义重。
2. **`{previous}` 在复用语境下的去留**：在常驻上下文已包含上一步时，`{previous}` 是废弃、保留为可选注入、还是改为可引用任意历史轮次？
3. **跨主进程重启的恢复契约**：重启后是“丢弃上下文重新冷启动（简单、安全）”，还是“持久化并恢复（复杂、需防污染）”？默认建议前者。
4. **session 分支与上下文视图的关系**：切换到分支 B 时，是否应为该角色在 B 上独立起一个 RPC 会话？分支合并 / 删除时如何回收？
5. **同角色并发的产品语义**：是串行排队（保序但慢）、还是并发多实例（快但资源翻倍）？默认建议 MVP 串行。
6. **上下文增长与成本控制**：长上下文下的 token 费用、缓存命中、截断 / 压缩策略，以及是否对调用方可见。
7. **失败与污染的边界**：某次 `task` 失败后，后续调用是继承“被污染的上下文”还是隔离重置？

## 6. 验证清单

> 以下清单用于（未来若开工时的）验证，不要求在本 deferred 文档阶段执行。

**验证（feasibility spike，1–2 人日）**
- [ ] 用 `pi --mode rpc` 成功建立长生命周期会话，并在多次提交 `task` 间复用同一上下文窗口；
- [ ] 复用上下文下，最终 `content` / `details` 的语义与一次性 `--no-session` 路径等价；
- [ ] 进程异常退出 / 主进程 `SIGTERM` 时 RPC 会话可被回收，无孤儿进程 / 句柄泄漏。

**受限 MVP（5–8 人日）**
- [ ] 单会话、单分支、单角色串行的 Single 模式走常驻 RPC；
- [ ] 空闲 `ttl` 自动回收且回退到一次性路径无误；
- [ ] 停止端口（`SIGTERM`→5s→`SIGKILL`、`stopped`/`interrupted` 状态）对常驻会话等价有效；
- [ ] 现有 `harness/run.mjs` 与 `harness/presentation.mjs` 通过（或仅因预期差异而有明确、受控的断言调整）；
- [ ] 真实 Pi 冒烟清单（`Ctrl+Alt+F` Fleet、浮层、`x` 停止确认、浏览器只读 Web UI）行为不变。

**生产就绪（15–25 人日）/ 全量（含精确跨重启 / 分支 / 同角色并行，20–35 人日）**
- [ ] 跨主进程重启恢复（按第 5 节既定策略）可重放或安全冷启动；
- [ ] session 分支隔离：切换 / 合并 / 删除分支时上下文视图正确建立与回收；
- [ ] 同角色并发：`Parallel` 下多同角色任务的排队或独立实例语义按既定策略生效，且结果顺序 / 50 KiB 上限 / 单失败不阻断等约束保持；
- [ ] 上下文增长有截断 / 压缩 / 成本可见机制；
- [ ] 失败污染边界按第 5 节决策实现；
- [ ] 两块自动 harness 与真实 TUI / 浏览器手测项全部通过，无回归。
